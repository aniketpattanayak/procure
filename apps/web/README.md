# @procure/web

Next.js 15 (App Router) web app for Procure: tenant workspace plus the Super Admin platform console. Built against `docs/contracts/phase-1-api.md`.

## Run

```bash
pnpm install
# API must be reachable at NEXT_PUBLIC_API_URL (default http://localhost:4000/api/v1, see root .env)
pnpm --filter @procure/web dev          # http://localhost:3000
pnpm --filter @procure/web typecheck
pnpm --filter @procure/web build && pnpm --filter @procure/web start   # runs the standalone server (output: standalone)
```

`NEXT_PUBLIC_API_URL` is read at build time. The API must allow `http://localhost:3000` as a CORS origin with credentials (`WEB_ORIGIN`).

Seed logins (from the API seed):

| Area | URL | Credentials |

| Tenant | `/login` | company code `acme`, `admin@acme.test` / `Admin@12345` |

Design system: `packages/ui` (`@procure/ui`) holds the tokens (`src/styles/tokens.css`, light and dark), the Tailwind preset (`tailwind-preset.cjs`) and the components, including `DataTable`. It is source-only and transpiled by Next via `transpilePackages`.

## Behaviour notes

- **Tokens**: the access token is held in memory only. The `rt` refresh cookie is httpOnly and sent with `credentials: 'include'`. On a 401 the client makes one refresh call (shared by concurrent requests and serialised across tabs with Web Locks, because reusing a rotated token revokes the whole family) and retries once. If refresh fails, it signs out and returns to the login page with `?next=`.
- **Errors**: problem JSON becomes an `ApiError` with `code`, `errors[]` and `meta`. Field errors map onto react-hook-form fields through `applyProblemToForm`. `AUTH.PASSWORD_CHANGE_REQUIRED` routes to `/change-password` (or `/platform/change-password`).
- **Lockout**: `AUTH.ACCOUNT_LOCKED` shows the unlock time from `meta.lockedUntil`, plus the minutes remaining.
- **Validation**: forms use the shared Zod schemas from `@procure/schema` through `zodResolver`. The password checklist reads its rules from the `Password` schema itself.
- **Feature gating**: sidebar entries for modules appear only when the key is in `/auth/me` `features`; they are hidden, not disabled.
- **Permissions (Phase 2)**: `/auth/me` carries `permissions` (`MyPermissions`). `usePermissions()` exposes `has(key)`, `hasAny`, `can(tab, action)`, `canView(tab)`, `permittedViews(tab, views)`, `fieldMode(form, field)` and `scope`; `<Can perm="admin.users:action.add">` (or `anyOf` / `allOf`, optional `fallback`) hides UI the user can't use. React reserves `key`, so the prop is `perm`. If `/auth/me` has no `permissions` (Phase 1 API), tenant admins hold everything and others nothing. Sidebar entries carry a `perm` (`<tab>:action.view`); the Masters group lists `GET /masters` entries the user can view (`master.<key>:action.view`) and links to `/masters/<key>`. Pages reached by direct URL are wrapped in `<RequirePermission perm=…>` (`components/guards.tsx`). List status chips use `<ViewChips tab=… options=…>` (`components/view-chips.tsx`), which shows only views the user holds and falls back to the first permitted one.
- **Tenant wording**: `/auth/me` `labels` are applied with `setLabelOverrides()` in the tenant shell, so a tenant override wins over `en.json` in every `t()` call. Edited on Settings > Labels.
- **Permission screen** (`features/permissions`): `PermissionWorkbench` (Role detail and User access) lists registry tabs grouped by `group` with search and a granted-count ring; the right pane has Buttons, Filters / status views and Field access per form, saved per tab with `PUT …/permissions/tabs/:tabKey`. Switching tabs with unsaved changes asks to save, discard or stay; leaving the page warns. For users, role grants show as read-only ticks with the role name (from `effective-permissions`), each key has Inherit / Allow / Deny, and fields add Editable (override role). `ScopeEditor` sets data scope (All locations, location tree with checkboxes and an "include sub-locations" switch per node, optional per-tab narrowing). `EffectivePanel` explains every key's source. On phones the tab list becomes a select.
- **Locations** (`features/locations`): the tree is built client-side from `GET /locations/tree` and rendered by `TreeView`, an ARIA tree (roving tabindex; Up/Down, Left/Right, Home/End, Enter selects, Space toggles in checklists, `*` expands siblings, type-ahead). Level names come from the `labels.location_levels` setting. Add, edit, move (tree picker that disables the node's own branch), deactivate (warns about the cascade), activate and delete (lists `meta.usedBy` on 409). `LIMIT_EXCEEDED.max_locations` shows the server message inline, and a usage strip shows `max_locations`.
- **Settings** (`features/settings`): `SettingRow`s grouped into Security, Flow, Procurement rules, Stock and Labels, with controls typed from `SettingsRegistry` (switch, number with range, select), reset to default per row, and one save bar for all changes. Labels holds the ordered location level editor and the wording editor (search `en.json` keys, set tenant wording, live preview).
- **Location switcher**: lists `GET /locations/tree?scope=mine` and keeps the choice per user in localStorage (`procure.location.<userId>`, wrapped in try/catch). Phase 4 lists read `useCurrentLocationId(userId)` from `src/lib/location.ts` (`null` = all of the user's locations).
- **Usage**: limits whose `featureKey` is off are hidden.
- **Impersonation**: "Login as tenant" requires a reason. The impersonation token is kept in `sessionStorage`, so it survives a reload in that tab only and leaves the Super Admin's own refresh cookie alone. A persistent banner shows while it is active, and Exit returns to the tenant detail page via the platform refresh cookie. Impersonation tokens are never refreshed; when one expires the session simply ends.
- **User limit**: a `LIMIT_EXCEEDED.*` response on create or activate shows the server's message inline (`user-limit-error`).
- **Usage bars**: amber from 80%, red at 100%; `null` means unlimited. Bars use `role="meter"` with a text value, so colour is never the only signal.
- **Theme**: System, Light or Dark, set from the profile menu (`data-theme` on `<html>`, stored in localStorage and applied before first paint).

## Phase 3 configuration

Screens built against `docs/contracts/phase-3-api.md` (workflow config, document types and numbering, audit):

```
src/features/workflows    /config/workflows (list) and /config/workflows/:docType (designer, lazy): lane canvas, stage panel,
                          effects/actors editors, simulation panel, versions and publish dialogs; pure helpers in model.ts
src/features/doc-types    /config/doc-types: list, create wizard, settings dialog (DocTypeSettings), activate/deactivate
src/features/numbering    /config/numbering: series per doc type, PatternEditor (token chips + live preview), LocationPicker, resolver
src/features/audit        /audit: filtered audit log (cursor paging), before/after DiffViewer, tamper check panel
```

- **Workflow designer**: stages are drawn as a vertical lane from "Document submitted" to "Approved". Consecutive stages with the same `parallelGroup` form one row (side by side, bracketed "run at the same time"); rows reorder by dragging the grip (dnd-kit, keyboard too) or the card menu (move up/down, left/right inside a row, run on its own, turn off, duplicate, delete). `+` between rows inserts a stage; the dashed button at a row's right adds a parallel stage. Cards show actors, "Everyone must approve", the `when` condition ("Only when …"), the SLA and how many automatic actions run; disabled stages are dashed and dimmed. The stage key follows the name until it is typed or published (then locked). Conditions use the Phase 2 `FormulaEditor` with a scope built by `combinedDefinition()` (header form + line form wrapped as the virtual grid `lines`, so `SUM(lines.amount)` type-checks), loaded from `/config/forms/<key>_header|_line` (draft, else published; falls back to `/forms/:key/render`). Effects not in `availableEffects` are listed disabled with "Available after <module>"; `route_to` is offered only in On rejection. Issues = instant local checks (`model.ts` `localIssues`, including formula compile errors) plus the server's `draftIssues` for the saved draft; publish is disabled while any remain. Save sends the row `version` (409 offers "Load latest"); undo/redo (Ctrl+Z / Ctrl+Shift+Z, typing coalesced), Ctrl+S saves, unsaved changes guard links and reload. Simulate opens a docked panel with the header and line forms rendered by `FormRenderer` (one synthetic form with the `lines` grid, so totals compute live); it simulates the saved draft or the published version, offers "Save and simulate" when there are unsaved edits, lists each stage's outcome and actors, and paints the route on the canvas (green rail = runs, hatched = skipped) until the definition changes.
- **Document types**: wizard name/plural/key (auto) → header-only or header + lines (item lines) → number pattern with live preview → create, then links to the header/line form builders, the workflow designer and numbering. `custom_forms` usage comes from `/auth/me` limits; a `LIMIT_EXCEEDED` response is shown inline. Settings dialog edits name, description, number label, sidebar visibility and icon, default document/item-wise columns (ordered), editable statuses and line cancel.
- **Numbering**: the next number column is the server's `preview`; the dialog previews the typed pattern locally (`renderPattern`, using `tenant.fy_start_month`) and asks `/config/numbering/:id/preview?locationId=&date=` for a saved series. "Which series applies?" resolves a picked location client-side the same way the server does (nearest active series at the location or an ancestor, else the all-locations series).
- **Audit**: filters map to `AuditQuery` (dates become start/end of day in the browser zone); impersonated entries carry a "by <name>" badge. The diff flattens objects and arrays of objects to dotted keys and marks each as added / removed / changed in text as well as colour.

- **Transport**: `features/reports/api.ts` calls the API, or the typed in-memory mock (`mock.ts`, a small reference run engine) when `NEXT_PUBLIC_REPORTS_MOCK=1` or localStorage `procure.reportsMock` = `1`.
- **Reports home**: built-in, mine (`isMine`) and shared with my roles, with search and a Mine / Shared / Built-in filter. Edit and delete follow the server's `canEdit`; anyone with `reports:action.build` can copy (built-ins are read-only, copying opens the builder with "Copy of …").
- **Viewer**: one row of parameters above the results, built from filters that expose `param` (date ranges with presets first, then a custom range; `within_location` as a location picker defaulting to all my locations; numbers, lists and yes/no by field type), plus a "Period" select when the definition has a `datePreset` (sent as `params.datePreset`). Applied values live in the URL (`?p.<key>=`), so links and reloads keep them. Results: virtualised TanStack table; with two or more group-by fields the first one heads collapsible group rows with subtotals (server `groups`, else summed client-side for sum/count/min/max); sticky totals row; drill-down links from `links[]` on the first column; "Load more" pages detail rows (200) with the cursor. Refetches keep the previous render dimmed.
- **Chart**: Recharts (lazy, viewer/builder/dashboard routes only), bar / stacked bar / line / area / pie. Series colours follow the dataviz reference palette in fixed order (`chart-theme.ts`, validated against this app's light `#FFFFFF` and dark `#181C22` surfaces; light aqua/yellow/magenta sit below 3:1, so the table is always shown with the chart). Dark mode uses its own selected steps. With two group-by fields and one value the other group becomes the series (location × month → one bar per location in each month); more than 6 series fold into "Other". Legend for 2+ series, hover tooltip (value first), compact Indian axis ticks (K / L / Cr), an `aria-label` summary on the figure.
- **Export**: `POST /exports` → toast "Export started" (link to /exports) → polls the job → toast "Your export is ready" with a download link (signed `fileUrl`). /exports lists jobs (polls while queued/running) with status, rows, expiry (7 days, or `expiresAt`) and download. The job row has no name, so the browser remembers the report name of exports it started (`procure.exportNames`).
- **Schedule**: daily 9:00 (`0 9 * * *`), weekly Monday (`0 9 * * 1`), monthly on the 1st (`0 9 1 * *`) or a custom 5-field cron; xlsx / csv / pdf; recipients = people (search) or email addresses, the current user pre-filled; the applied parameters are saved with it. Existing schedules are listed and removable.
- **Builder**: sources grouped Documents / Document lines / Masters / Engine; field tree grouped by `path` (Item › Category) with search. Fields drag (dnd-kit) onto Columns, Group by, Filters, Sort, or use the `+` menu (keyboard and phones). Chips reorder by drag. Grouping by a field adds it as a column (group columns lead, in group order) and turns plain numeric columns into sums. Inspector: column heading / summary / format / width; filter condition and value by field type, "Let viewers change this" (param label, key, required); sort direction; chart (type, categories, up to 6 values); report settings (totals, default period, row limit). Local issues (ungrouped columns, missing filter values, bad param keys, chart fields) block preview and save. Preview = `POST /reports/preview` 600 ms after the last change. Save: name, key (follows the name until typed; locked after create), description, share with roles (`reports:action.share`). Date bucketing uses the catalogue's `<field>.month` / `.year` fields.
- **Dashboards**: `/dashboard` renders `GET /dashboards/mine` on a 12-column grid (80 px rows) from lg; below that widgets stack in reading order at their designed height (key figures two per row on tablets). Widgets: `kpi` (value, % change vs previous period from `deltaPct`), `chart` (always runs the report so a second group can become the series), `table`, `inbox_counts` (the Phase 3 `ApprovalsWidget`, unchanged ids `inbox-widget-*`), `doc_counts` (one type, or every type when no `docTypeKey`; every status links to `/docs/<type>?status=<key>`). Each widget loads on its own with a skeleton. If the dashboards API fails the page falls back to the Phase 3 cards.
- **Designer** (`dashboards:action.edit`): add widgets (first free slot), move by dragging the handle on the top edge (snaps to cells, a dashed target shows where it lands) or arrow keys, resize from the corner or Shift+arrows (announced in a live region), configure in the side panel (type, title, report, period override, doc type, x/y/w/h). Overlaps push widgets down and the grid compacts upward. Share: per role "Can open" and "Home page" (`isDefaultForRoleIds`, implies shared). Built-in or other people's dashboards save as a new copy.
